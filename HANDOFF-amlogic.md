# HANDOFF — Amlogic-бэкенд: отладка «почему падает вычитка» (2026-10-29)

Ветка `feature/amlogic-backend`, базовый коммит `226631d`
(«feat(amlogic): second platform backend — Capsula Mini on A113X»).
Рабочее дерево поверх коммита содержит диагностические расширения
пасстру `aml` (см. «Незакоммичено»).

## TL;DR

Вычитка падает потому, что у **здоровой** колонки ровно одно
download-окно ~700 мс на включение (`try_auto_burn=update 700 450`) и
**ничто его не продлевает**. Однопроходный захват (PR2-дизайн) в него
не помещается архитектурно. Вендорский флоу работает только потому,
что работает с **незагружающимися** платами: стоковый `storeboot` при
нечитаемом ядре проваливается в `run update`, и окна идут по кругу —
цитата из flasher.sh: «Стоковый bootcmd не кончается, он падает в
режим прошивки». Колонка возвращена в сток (env восстановлен,
подтверждено монитором: одно окно на включение → Linux).

## Установленные факты (все — на живом железе, macOS/arm64)

1. **Окно жёсткое и не продлевается.** Проверено: identify с любым
   интервалом (100/300/700 мс), bulkcmd-трафик, непрерывные RAM-потоки,
   TPL-download + media-пакет. Всё умирает на согласованном бюджете
   ~250–350 мс от открытия сессии ≈ 500–700 мс от старта гаджета
   (энумерация macOS съедает 200–400 мс).
2. **Скорость внутри окна высокая**: `upload mem` 4 МиБ — 161 мс
   (~26 МБ/с). Второй 4-МиБ поток подряд умирает на +306 мс
   (`kIOReturnNotResponding` 0xe00002d9) — стена абсолютная, не
   idle-саспенд.
3. **`upload store` хуже простого пути**: умирает раньше/чаще (паузы
   NAND-staging). Рабочий путь вычитки — как у flasher.sh:
   `echo; nand read <ram> <off> <n>` (shell) + `upload mem` (стрим).
4. **Хост не виноват**: вендорский `update_macos` (разобран,
   arm64-слайс) — тот же код, `AmlDisableSuspendForUsb` — заглушка
   «not implemented». Дело в состоянии платы, не в macOS/libusb.
5. **saveenv работает и переживает перезагрузку** (проверено чтением
   env обратно). Манипуляции с bootcmd — рутина flasher.sh.

## Реверс вендорского тула (../update, ../update_macos, ../flasher.sh)

- `OpenUsbDevice` = только `usb_open` (без claim/set_configuration).
  Identify = control 0xc0/0x20, wLength ≤ 8, timeout 5000 —
  байт-в-байт наш.
- `update mread mem <addr> normal <size> <file>` внутри себя строит
  **`upload %s %s %s 0x%lx`** и шлёт через **BULKCMD (0x34)**, затем
  `ReadMediaFile` — цикл 64-КиБ `AmlReadMedia` (0x33 + bulk-IN). Тот же
  проводной паттерн, что у нашего `upload_read`.
- flasher.sh читает большие области ТОЛЬКО через `echo; nand read` +
  `mread mem` (никакого `upload store`); пишет — `mwrite` в RAM
  кусками MWRITE_CHUNK=8 МиБ + `nand write` по сырым смещениям.
- `ensure_online` (identify перед каждой операцией) + `poll_for_device`
  (identify каждые 100 мс) — модель «окно на операцию».
- `AmlResetDev` («reset worldcup device») вызывается из `main` —
  вендор сам делает port reset.

## Состояние железа

**Колонка в стоке**: bootcmd=run storeboot, boot_part=boot_a (проверено
чтением env; финальный монитор показал штатное «одно окно → Linux»).
NAND не писался вообще (никаких download store / nand write).
Меняли только две переменные окружения, обе возвращены.

## Незакоммичено (рабочее дерево)

`crates/jb-cli/src/amlogic.rs` — расширения пасстру `aml`
(полезные полевые инструменты, стоит закоммитить после чистки):
- `dlmem <size>` — probe-download в DRAM (TPL arm + media + статус);
- `cycle <n>` — циклы перезахода в окно (см. «следующий шаг»);
- `upload mem` в пасстру поднят до 8 МиБ (как MWRITE_CHUNK вендора);
- hexdump-голова 4 КиБ вместо 512 Б;
- есть один `unused_mut` warning — почистить перед коммитом.

Спец-файл «Amlogic A113X USB Protocol Specification RU.md» в корне —
**не коммитить** (решение владельца).

## Что признано сломанным в текущем бэкенде (226631d)

- `jb_core::aml::backup` (однопроходный захват) — не помещается в
  окно; нужен цикл «окно-чекпоинт».
- `amlogic::store::write_store` (`download store` одним куском) —
  непрерываемо и, по реверсу тула, arm должен идти через TPL-канал;
  заменить на путь flasher.sh: download/mwrite в RAM кусками 8 МиБ +
  `echo; nand write <ram> <data_off+pos> <n>` (прерываемо и обратимо
  по куску).
- bring_up — уже норм (горячий цикел ловли), но для capture-цикла
  нужен budget-aware стриминг (выходить по чанкам ДО стены).

## Следующие шаги (по приоритету)

1. **Довести cycle до рецепта стека**: `run try_auto_burn`
   (fire-and-forget) → 300 мс → **`s.reset()` (port reset)** → ловим
   переэнумерацию → свежая сессия → 4 МиБ стрим. Если бюджет окна
   обновляется — это и есть транспорт для захвата без передёргиваний
   питания и без правок env. (В моём тесте 18:08 port reset не
   посылался — это главный неиспробованный кандидат.)
2. Если port-reset-переход работает: переписать захват как цикл
   `nand read 4–8 МиБ` + `upload mem` + чекпоинт на диск, с
   бюджет-таймером ~250 мс на сессию.
3. Если не работает: fallback — чекпоинт-захват с ручным
   передёргиванием питания (≈8–13 МБ за окно; полный захват ~30–50
   включений; урезать опциональный `nand-full.raw.bin`).
4. Параллельно: вопрос «почему bootcmd='run try_auto_burn; reset' не
   даёт окон на тёплых циклах» мгновенно решается serial-консолью
   колонки (ttyS0 115200; у владельца есть опыт с UART на rockchip).
5. Путь записи — по образцу mwrite_to_ram флэшера (п. выше).
6. Обновить AGENTS.md (корневой) разделом про окно/стену, когда
   архитектура устоится.
