## 1. Назначение

Документ описывает USB-протокол обмена между хостом и SoC Amlogic A113X
в режиме загрузки. Он охватывает перечисление устройства, control-запросы,
bulk-передачу, идентификацию, доступ к памяти, media-передачу и
последовательность загрузки boot-образа.

Документ применяется к вендорскому инструменту `update` версии 1.5
(2017/05) и совместимым реализациям хоста. Форматы хранения, таблицы
разделов, NAND ECC и драйверы операционных систем выходят за рамки
документа.

Разделы нормативны, если не помечены как информативные. Примеры
информативны.

## 4. Обзор протокола

Устройство перечисляется как vendor-specific USB-устройство с одной
конфигурацией и одним интерфейсом. Endpoint 0 обслуживает вендорские
control-запросы; endpoint `0x81` — bulk IN; endpoint `0x02` — bulk OUT.

Типичная сессия:

1. Хост обнаруживает устройство по VID и PID.
2. Хост выбирает конфигурацию 1 и захватывает интерфейс 0.
3. Хост отправляет Identify и проверяет ответ.
4. Хост выполняет операции с памятью, media, TPL или bulk.
5. Хост дожидается финального статуса перед отключением.

BootROM и TPL используют общий формат control-запросов. Large-memory
передачи характерны для BootROM; поддержка в TPL зависит от прошивки.
См. раздел 13.

## 5. Конфигурация USB

| Параметр | Значение |
|---|---|
| VID:PID | `1b8e:c003` |
| bcdUSB | `0x0200` |
| bDeviceClass | `0x00` (определяется интерфейсом) |
| Конфигурация | 1 |
| Интерфейс | 0, vendor-specific |
| Bulk IN endpoint | `0x81`, максимальный пакет 512 байт |
| Bulk OUT endpoint | `0x02`, максимальный пакет 512 байт |
| Скорость | 480 Мбит/с (USB 2.0 high speed) |

Хост ДОЛЖЕН выбирать устройство по VID и PID. Строки product и
manufacturer МОГУТ быть пустыми у boot ROM; хост НЕ ДОЛЖЕН требовать их
наличия.

Хост ДОЛЖЕН выбрать конфигурацию 1 перед bulk-передачей и СЛЕДУЕТ
захватить интерфейс 0. Control-запросы отправляются на endpoint 0 и не
требуют захвата интерфейса.

## 6. Соглашения

- Все многобайтные поля — little-endian.
- Таймауты выражены в миллисекундах.
- Длины выражены в байтах.
- Зарезервированные поля ДОЛЖНЫ быть заполнены нулями хостом и
  игнорироваться устройством.
- Control-запросы используют vendor-тип и получателя device.
- Строки статуса — ASCII; хост ДОЛЖЕН отбрасывать завершающие NUL перед
  сравнением.
- Хост ДОЛЖЕН использовать фактическую длину ответа, если устройство
  вправе вернуть меньше запрошенного.
- Короткая control- или bulk-передача является ошибкой, если операция
  явно не допускает этого.

## 7. Формат control-запроса

| Поле | Описание |
|---|---|
| `bmRequestType` | `0x40` — host-to-device; `0xc0` — device-to-host. |
| `bRequest` | Код операции из приложения A. |
| `wValue` | Параметр операции; часто старшее слово адреса. |
| `wIndex` | Индекс операции; часто младшее слово адреса, страница или метаданные. |
| `wLength` | Длина данных или запрошенного ответа. |
| Data | Payload операции. |

Вендорские запросы используют `recipient = device`. Хост НЕ ДОЛЖЕН
использовать standard, class или interface recipient для операций этого
документа.

## 9. Identify

### 9.1 Запрос

| Поле | Значение |
|---|---|
| `bmRequestType` | `0xc0` |
| `bRequest` | `0x20` |
| `wValue` | 0 |
| `wIndex` | 0 |
| `wLength` | 4 (по умолчанию)..8 |
| Таймаут | 5000 |

Хост СЛЕДУЕТ запрашивать 4 байта для минимального ответа и МОЖЕТ
запрашивать до 8 байт для получения необязательных полей.

### 9.2 Ответ

| Смещение | Размер | Поле | Описание |
|---|---|---|---|
| 0 | 1 | V0 | Компонент версии 0. |
| 1 | 1 | V1 | Компонент версии 1. |
| 2 | 1 | V2 | Компонент версии 2. |
| 3 | 1 | V3 | Компонент версии 3; также включает необязательные поля. |
| 4 | 1 | PWD_REQ | 1 — устройство требует пароль. |
| 5 | 1 | PWD_OK | 1 — пароль принят; присутствует при `wLength > 5`. |
| 6 | 1 | MAP6 | Байт page map 6; присутствует при `wLength > 7` и ненулевом байте 7. |
| 7 | 1 | MAP7 | Байт page map 7. |

Вендорский инструмент отображает четыре байта версии как десятичные
компоненты, например `0.7.0.16`.

Если V0..V3 все нулевые, ответ недействителен. Хост ДОЛЖЕН отклонить его.
Ответ из 4 байт действителен и не содержит необязательных полей.

Байт V3 также управляет интерпретацией необязательных полей: если V3
равен нулю, хост ДОЛЖЕН игнорировать байты 4..7. Если V3 ненулевой, хост
МОЖЕТ интерпретировать байты 4..7 согласно таблице.

## 10. Аутентификация паролем

### 10.1 Запрос

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x35` |
| `wValue` | Сумма всех байт пароля по модулю 65536 |
| `wIndex` | 0 |
| `wLength` | Длина пароля, 1..64 |
| Data | Байты пароля |
| Таймаут | 8000 |

Хост ДОЛЖЕН вычислять `wValue` как 16-битную сумму байт пароля.

### 10.2 Процедура

1. Отправить запрос с паролем.
2. Повторно отправить Identify после короткой паузы.
3. Пароль принят, если байт PWD_OK равен 1.

Вендорский инструмент выполняет не более двух попыток и ждёт 5 секунд
между ними. Хосту СЛЕДУЕТ соблюдать то же ограничение, чтобы не вызвать
блокировку.

### 11.1 Запрос

| Поле | Значение |
|---|---|
| `bmRequestType` | `0xc0` |
| `bRequest` | `0x40` |
| `wValue` | 0 |
| `wIndex` | Индекс страницы |

## 12. Доступ к памяти

### 12.1 Чтение памяти

| Поле | Значение |
|---|---|
| `bmRequestType` | `0xc0` |
| `bRequest` | `0x02` |
| `wValue` | `addr >> 16` |
| `wIndex` | `addr & 0xffff` |
| `wLength` | 1..64 |
| Таймаут | 5000 |

Хост читает не более 64 байт за запрос. Для больших диапазонов хост
ДОЛЖЕН разбивать диапазон на блоки по 64 байта и увеличивать адрес на
длину каждого блока.

### 12.2 Запись памяти

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x01` |
| `wValue` | `addr >> 16` |
| `wIndex` | `addr & 0xffff` |
| `wLength` | 1..64 |
| Data | Записываемые байты |
| Таймаут | 5000 |

Хост пишет не более 64 байт за запрос и ДОЛЖЕН использовать то же
разбиение, что и при чтении.

### 12.3 Запуск

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x05` |
| `wValue` | `addr >> 16` |
| `wIndex` | `addr & 0xffff` |
| `wLength` | 4 |
| Data | 4-байтный адрес; младший байт OR `0x10` |
| Таймаут | 50000 |

Хост ДОЛЖЕН убедиться, что по целевому адресу находится корректный
исполняемый код. Выполнение произвольного кода может необратимо изменить
состояние устройства.

## 13. Large memory

### 13.1 Заголовок

| Смещение | Размер | Поле |
|---|---|---|
| `0x00` | 4 | Адрес назначения |
| `0x04` | 4 | Длина передачи |
| `0x08` | 4 | Контрольная сумма (младшие 16 бит) |
| `0x0c` | 4 | Размер блока |

Контрольная сумма — сумма little-endian 32-битных слов; хвост 1..3 байта
добавляется как маскированное слово. Размер блока в заголовке ДОЛЖЕН
совпадать с `wValue`.

### 13.2 Чтение

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x12` |
| `wValue` | Размер блока, 1..0x1000 |
| `wIndex` | Количество блоков = `ceil(length / block size)` |
| `wLength` | 16 |
| Таймаут | 50000 |

После control-запроса хост читает `length` байт из bulk IN.

### 13.3 Запись

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x11` |
| `wValue` | Размер блока, 1..0x1000 |
| `wIndex` | Количество блоков = `ceil(length / block size)` |
| `wLength` | 16 |
| Таймаут | 50000 |

После control-запроса хост пишет `length` байт в bulk OUT. Хост МОЖЕТ
разбивать payload на блоки `block size`; последний блок МОЖЕТ быть короче.

### 13.4 Поддержка стадий

Large-memory передачи в первую очередь используются BootROM. Реализация
TPL МОЖЕТ не поддерживать `0x11` или `0x12`; хост ДОЛЖЕН обработать
таймаут и переподключиться.

## 14. Канал TPL-команд

### 14.1 Команда

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x30` |
| `wValue` | Метаданные команды |
| `wIndex` | Метаданные команды |
| `wLength` | 64 |
| Data | Строка команды, NUL-терминированная, дополненная нулями до 64 байт |
| Таймаут | 50000 |

`wValue` и `wIndex` определяются командой. Эта спецификация не задаёт
для них единое значение. Строка команды вместе с завершающим NUL ДОЛЖНА
помещаться в 64 байта.

### 14.2 Статус

| Поле | Значение |
|---|---|
| `bmRequestType` | `0xc0` |
| `bRequest` | `0x31` |
| `wValue` | Метаданные команды |
| `wIndex` | Метаданные команды |
| `wLength` | 64 |
| Таймаут | 60000 |

Устройство возвращает ASCII-строку статуса. Хост ДОЛЖЕН опрашивать
статус, пока ответ начинается с `Continue:`, и прекращать опрос при
финальном статусе или истечении таймаута.

## 15. Канал bulk-команд

### 15.1 Команда

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x34` |
| `wValue` | 0 |
| `wIndex` | 2 |
| `wLength` | 64 |
| Data | Строка команды, NUL-терминированная, дополненная нулями до 64 байт |
| Таймаут | 50000 |

Строка команды вместе с NUL ДОЛЖНА помещаться в 64 байта. Более длинная
строка усекается устройством; хост ДОЛЖЕН отклонять её.

### 15.2 Статус

Хост читает до 512 байт из bulk IN.

| Статус | Значение |
|---|---|
| `Continue:34` | Команда ещё выполняется; подождать 3 секунды и прочитать снова. |
| `success` | Команда успешно завершена. |
| Любой другой текст | Ошибка; текст является сообщением об ошибке. |

## 16. Media-передача

### 16.1 Чтение

| Поле | Значение |
|---|---|
| `bmRequestType` | `0xc0` |
| `bRequest` | `0x33` |
| `wValue` | Размер блока (`0x1000`) |
| `wIndex` | Количество блоков = `ceil(length / block size)` |
| `wLength` | 16 |
| Таймаут | 5000 |

Заголовок:

| Смещение | Размер | Поле |
|---|---|---|
| `0x00` | 4 | 0 |
| `0x04` | 4 | Длина |
| `0x08` | 8 | 0 |

После control-запроса хост читает ровно `length` байт из bulk IN.
Короткое чтение является ошибкой.

### 16.2 Запись

| Поле | Значение |
|---|---|
| `bmRequestType` | `0x40` |
| `bRequest` | `0x32` |
| `wValue` | 1 |
| `wIndex` | `0xffff` |
| `wLength` | 32 |
| Таймаут | 5000 |

Заголовок:

| Смещение | Размер | Поле |
|---|---|---|
| `0x00` | 4 | Номер попытки, 0..2 |
| `0x04` | 4 | Длина блока |
| `0x08` | 4 | Номер последовательности, сдвинутый влево на 4 |
| `0x0c` | 4 | Контрольная сумма |
| `0x10` | 4 | `ef 00 00 01` |
| `0x14` | 12 | 0 |

Контрольная сумма использует алгоритм из раздела 13.1. Хост пишет блок
в bulk OUT, затем читает до 512 байт из bulk IN.

| Статус | Действие хоста |
|---|---|
| `Continue:32` | Подождать 500 мс и прочитать статус снова. |
| `OK!!` | Блок принят; перейти к следующему. |
| Любой другой текст | Ошибка блока; повторить, но не более трёх попыток. |

Номер последовательности увеличивается на каждом блоке. Размер блока
НЕ ДОЛЖЕН превышать 64 КиБ.

## 17. Последовательность загрузки boot-образа

Хост загружает boot-образ так:

1. Передать образ в RAM через large-memory запись (раздел 13.3).
2. Использовать адрес назначения и размер блока, требуемые образом.
3. Отправить TPL-команду `nand` (раздел 14.1).
4. Дождаться финального TPL-статуса перед отключением.

Пример конфигурации: адрес назначения `0x49000000`, размер блока `0x2000`.
Эти значения информативны; хост ДОЛЖЕН использовать значения, требуемые
целевым образом и устройством.

Хост ДОЛЖЕН проверить образ и состояние устройства перед началом
энергонезависимой записи. Неудачная или прерванная запись boot-образа
может сделать устройство неспособным загрузиться.

## 18. Таймауты и повторы

| Операция | Таймаут хоста |
|---|---|
| Identify | 5000 |
| Чтение/запись памяти | 5000 |
| Обработчик памяти (сторона устройства) | 50000 |
| Large memory | 50000 |
| TPL command | 50000 |
| TPL status | 60000 |
| Password | 8000 |
| Chip info | 8000 |
| Media read/write | 5000 |
| Bulk command | 50000 |

Хост НЕ ДОЛЖЕН повторять destructive-операцию после таймаута без
повторной идентификации и проверки состояния устройства. Безопасные
операции чтения МОГУТ быть повторены после переподключения.

## 19. Обработка ошибок

- Недействительный ответ Identify, все нулевые байты версии или короткий
  ответ там, где требуется полный, ДОЛЖНЫ считаться ошибкой протокола.
- Ответ статуса, начинающийся с `Continue:`, не является ошибкой; хост
  ДОЛЖЕН опросить снова после указанной паузы.
- Ответ статуса, отличный от документированных строк успеха, является
  ошибкой.
- Короткое bulk-чтение или bulk-запись в media-операции является ошибкой.
- При таймауте control- или bulk-передачи хост ДОЛЖЕН остановить
  операцию, закрыть устройство и выполнить переподключение перед повтором.
- Хост НЕ ДОЛЖЕН отправлять новую команду, пока предыдущий статус не
  завершён.

## 20. Безопасность

- Аутентификация паролем — это plaintext-проверка; она не обеспечивает
  конфиденциальность.
- Физический доступ по USB позволяет читать и изменять память устройства.
- Устройство МОЖЕТ применять secure boot; хост НЕ ДОЛЖЕН предполагать,
  что успешно переданный образ будет выполнен.
- Хост ДОЛЖЕН проверять подписи и целостность прошивки перед
  энергонезависимой записью.
- Строки ошибок и статусов могут содержать текст, специфичный для
  устройства; хост НЕ ДОЛЖЕН исполнять или интерпретировать их как
  команды.

## 21. Ограничения

- Ответ chip info МОЖЕТ быть короче запрошенной длины.
- Поддержка large memory зависит от стадии загрузки и прошивки.
- Метаданные TPL-команд зависят от команды.
- Поведение повторов media write за пределами правила трёх попыток
  (раздел 16.2) зависит от устройства.
- Документ не описывает форматы хранения, таблицы разделов, ECC и
  форматы подписи образов.
